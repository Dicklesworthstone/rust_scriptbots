# Extreme-software-optimization serial loop

This file is the durable control plane for the user-requested 10+ applications of
`extreme-software-optimization`, orchestrated through `repeatedly-apply-skill`.

## Non-negotiable protocol

- The orchestrator does not implement an optimization pass. Each pass is assigned to one fresh
  subagent, runs serially, and has a disjoint lifetime from every other pass.
- Profiling precedes pass 1. No hypothesis becomes a patch until current DSR evidence attributes a
  material cost to the exact workload and the negative-evidence retry predicate permits it.
- One causal lever per commit. Each commit must be independently revertible.
- All formatting, compilation, linting, tests, UBS/Miri, and performance work execute only through
  a clean, exact-commit, pinned DSR profile. No GitHub Actions, direct Cargo, RCH, direct UBS, or
  direct performance-wrapper invocation is admissible.
- A pass is kept only when focused and broad conformance remain green, deterministic digests and
  contract identities are unchanged, the exact-class performance gate is stable, and the measured
  opportunity score clears the campaign threshold. Otherwise it is reverted or left unmerged and
  recorded in the negative-evidence ledger with a falsifiable retry predicate.
- Do not retry until green. Noise or infrastructure failure permits at most the explicitly declared
  retry in the relevant negative-ledger row; it never converts a result into a win.

## Per-pass closeout checklist

1. Re-read the relevant negative-ledger rows and show the retry predicate is satisfied.
2. Record the current profiler attribution and an explicit opportunity score.
3. Assign exactly one fresh subagent and reserve only its edit surface.
4. Review the diff for semantic scope, determinism, allocations, and concurrency effects.
5. Commit the single lever with `DSR proof pending`; update this row before starting another pass.
6. Run one exact-commit DSR batch containing focused conformance, broad conformance, and the
   appropriate performance matrix.
7. Mark `keep`, `revert`, `rejected`, or `inconclusive`; cite raw artifacts and typed verdicts.
8. For any non-keep, add the negative-evidence row and its concrete retry predicate before the next
   pass. For a keep, record both the focused and broad green gates plus the stable measured delta.
